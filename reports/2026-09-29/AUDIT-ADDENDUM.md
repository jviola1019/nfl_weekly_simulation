# Audit addendum (2026-09-29)

New defects found during Phase 0 Task 3 (test-harness triage) and the Phase 0 final review, after the test suite began loading every `R/` module and failing on unapproved skips. None of them is in `reports/2026-09-28/AUDIT.md` (on `docs/overhaul-spec`, PR #191). IDs continue that audit's series. Each ID is cited by a `KNOWN-DEFECT` skip in `tests/testthat/`, and the phase that fixes the ID removes the skip.

Severity uses the same scale as the audit: **Critical** changes shown numbers or invalidates claims; **High** is wrong behavior or a false claim; **Med** is a risk or drift; **Low** is hygiene.

## 1. Game model

| ID | Sev | Finding | Evidence |
|---|---|---|---|
| M14 | Med | `resolve_nfl_context()` fails for every date. nflreadr `gametime` is `"HH:MM"` (no seconds). `parse_kickoff_times()` pastes `gameday` and `gametime` and calls `parse_datetime()`, which tries `lubridate::ymd_hms()` and then `ymd()`. Both return NA for `"2024-09-05 20:20"`, so every `kickoff_local` is NA (all 285 rows of the 2024 schedule), `get_week_boundaries()` returns 0 rows, and the resolver returns `"Could not calculate week boundaries"`. `ymd_hm()` parses the same string. No production script calls the resolver today; `CLAUDE.md` lists it as the date-resolution module. The tests hid this because they called `skip()` when resolution failed, and `get_week_boundaries` wrapped its expectations in `tryCatch(error = skip)`. | `R/date_resolver.R:162,168` (parsers), `:197-200` (paste), `:243-253` (NA rows dropped), `:373-378` (error); reproduced 2026-09-29 with lubridate 1.9.4 and nflreadr 1.5.0; `tests/testthat/test-date-resolver.R` (6 tests) |
| M15 | Low | `load_player_snap_percentages()` always returns 0 rows. nflreadr `load_participation()` (1.5.0) is play-level: it has `n_offense` (players on the field, 10–13) and no player-name column. The loader picks `n_offense` as the snap-count column, so it never reaches `calculate_snap_pct_from_plays()`. It then finds no `full_name`/`player_name`/`gsis_id` column and returns the empty default. For 2024 DAL weeks 1–4, the data has 334 plays and the loader returns 0 rows; `calculate_snap_pct_from_plays()` fed the same 334 plays returns 38 player rows. Snap weighting is off by default (`USE_SNAP_WEIGHTED_INJURIES <- FALSE`), so production output is unaffected; turning it on would silently do nothing. The test hid this because its expectations sat inside `if (nrow(snap_data) > 0)`. | `injury_scalp.R:1384-1386` (snap column), `:1388-1394` (play-level branch never reached), `:1398-1406` (empty default); `config.R:326`; `tests/testthat/test-snap-weighting.R` ("snap percentages have expected structure") |
| M16 | High | The offensive injury penalty is clamped the wrong way, so any team with even one listed injury loses at least 1.5 offensive points. `base_pen` is negative (OUT −0.50, DOUBTFUL −0.35, QUESTIONABLE −0.20, LIMITED −0.10) × `pos_wt` (positive), and `inj_off_pts = pmax(pmin(inj_off_pts_raw * w, -1.5), -4.0)` confines the result to [−4.0, −1.5]. One questionable WR (−0.20 × 1.05 × w = 1/9 ≈ −0.023) becomes −1.5. The defensive twin, `pmax(pmin(x, +1.5), 0.0)`, caps at [0, 1.5], which suggests the intended offensive bounds were [−1.5, 0]. Separately, `inj_off_pts_raw` sums `pen` over every position except QB, so defensive players' injuries also lower the team's *offensive* points. Most teams list someone every week, so both teams usually take −1.5 or more: win-probability effects partly cancel, but modeled totals are biased down by ≈3 points per game, and games where one team has no injury rows are skewed. Suspected by the Phase 0 final fix-wave implementer; confirmed by the controller from source on 2026-09-29 (no run-time reproduction yet). | `NFLsimulation.R:3403-3408` (`base_pen`), `:3431` (`pen`), `:3445` (offensive sum over all non-QB positions), `:3457` (clamp), `:3458` (defensive twin), `:4512-4513` (applied to totals) |
